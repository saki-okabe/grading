# 第5回課題（プレ）SWOT：採点基準

## 1. 課題内容

大学祭における出店企画について、出店しようとする類似店舗の現状を調査し、目標を実現するための方向性を分析する。

課題の目標は「来場者と出店者の双方にとって、記憶に残る大学祭体験を創出すること」である。

プレ提出で確認する作業は次の3種類である。

1. 類似店舗の現状調査を踏まえてSWOT分析を行う
2. SWOT分析の結果を組み合わせて「取り得る戦略」をまとめる
3. 目標を実現するための明確な方向性を提案する

課題文の（4）にある教え合いの記録は、プレ提出の採点対象に含めない。

## 2. 採点方針

このプレ課題は2点満点とする。内容の良し悪し、分析の深さ、戦略の実現可能性、文章表現、図表の見た目は点数に使用しない。指定された3種類の作業に取り組んでいるかだけを判定する。

- 3種類すべてに取り組んでいる：2点
- 1種類または2種類に取り組んでいる：1点
- 3種類とも確認できない：0点
- 提出なし：0点
- PDF以外：作業点から1点減点
- 遅延：減点なし

```text
点数 = max(0, 作業点 + PDF形式減点)
```

## 3. 判定値

P1～P3には次の値だけを使用する。

- `Yes`：該当する作業に取り組んだ形跡が確認できる。
- `No`：該当する作業の形跡が確認できない。
- `判定不能`：不鮮明、見切れ、ページ不足などにより判断できない。

`Partial`は使用しない。

---

## 4. 観察項目

### P1_SWOT分析への取組

SWOT分析とは、対象となる店舗や企画の状況を次の4分類で整理する方法である。

- Strengths／強み：対象の内部にある有利な点
- Weaknesses／弱み：対象の内部にある不利な点
- Opportunities／機会：対象の外部環境にある有利な状況
- Threats／脅威：対象の外部環境にある不利な状況

日本語、英語、略号のいずれで書かれていてもよい。

次のいずれかが確認できれば`Yes`とする。

- 「SWOT分析」という見出しと分析内容がある。
- 強み、弱み、機会、脅威の4区分を持つ表や図がある。
- S、W、O、Tの区分ごとに項目が記載されている。
- 一般的なSWOT表と形式が異なっていても、4つの観点で現状を整理しようとした形跡がある。

次の問題があっても取組を確認できれば`Yes`とする。

- 4区分の一部の項目数が少ない。
- 内部環境と外部環境の分類に誤りがある。
- 強みと機会、弱みと脅威が一部混同されている。
- 調査内容が浅い。
- 類似店舗との関係が不明確である。
- 表ではなく箇条書きで書かれている。

- 「SWOT」という見出しだけで分析項目がない：`No`
- 強みなど1区分だけしかなく、4分類を使おうとした形跡がない：`No`
- SWOTと無関係な感想だけが書かれている：`No`
- 画像が不鮮明、見切れまたはページ不足で分類や項目を確認できない：`判定不能`

### P2_取り得る戦略の作成

「取り得る戦略」とは、SWOT分析で得た要素を組み合わせ、対象となる店舗や企画がどのように行動できるかを整理したものである。一般的には次の組合せがある。

- SO戦略：強みを使って機会を活かす
- ST戦略：強みを使って脅威へ対応する
- WO戦略：機会を活かして弱みを補う
- WT戦略：弱みと脅威による悪影響を避ける

「クロスSWOT」「SWOTクロス分析」「戦略案」などの名称でもよい。

次のいずれかが確認できれば`Yes`とする。

- 「取り得る戦略」「クロスSWOT」「戦略案」などの見出しと内容がある。
- SO、ST、WO、WTの組合せによる戦略が記載されている。
- SWOT分析で挙げた複数の要素を組み合わせて行動案を作っている。
- 4種類すべてがなくても、複数のSWOT要素から戦略を作ろうとした形跡がある。

次の問題があっても取組を確認できれば`Yes`とする。

- SO、ST、WO、WTの一部しかない。
- 組み合わせ方に誤りがある。
- 戦略が抽象的である。
- SWOT表の項目との対応が不十分である。
- 戦略の実現可能性に疑問がある。

- 「取り得る戦略」という見出しだけで内容がない：`No`
- SWOT項目をそのまま再掲しただけで、行動や方針がない：`No`
- SWOT分析だけで戦略案がない：`No`
- どの記載が戦略に該当するか、画像から判断できない：`判定不能`

### P3_明確な方向性の提案

方向性の提案とは、SWOT分析と取り得る戦略を踏まえて、課題の目標を実現するために企画をどの方向へ進めるかを文章で示すことである。単語や名称だけでなく、少なくとも「何を目指し、どのような考え方で企画するか」が読める記載を対象とする。

次のいずれかが確認できれば`Yes`とする。

- 「方向性」「提案」「方針」「戦略のまとめ」などの見出しと文章がある。
- 企画をどのような方向へ進めるかが文章で示されている。
- SWOT分析または戦略案を踏まえた最終的な方針がある。
- 来場者と出店者の体験を良くするための方向性を示そうとした形跡がある。

次の問題があっても取組を確認できれば`Yes`とする。

- 方向性が抽象的である。
- 文章が短い。
- SWOT分析とのつながりが弱い。
- 来場者または出店者の一方に偏っている。
- 具体策の記載が不足している。

- 見出しだけで内容がない：`No`
- 「頑張る」「楽しくする」などの単語や短い感想だけで、企画の方向を読めない：`No`
- SWOT表や戦略案だけで、最終的な方向性の記載がない：`No`
- 文章が不鮮明、見切れまたはページ不足で内容を判断できない：`判定不能`

## 5. 誤判定の防止

- 同じSWOT表だけを、根拠なくP1、P2、P3のすべてに数えない。
- P1は、強み、弱み、機会、脅威による現状整理を確認する。
- P2は、SWOT要素を組み合わせた行動案や戦略を確認する。
- P3は、課題の目標を実現するための最終的な方向性を確認する。
- 内容に誤りがあっても、該当する作業への取組を確認できれば`Yes`とする。
- 見出しだけで内容がなければ`No`とする。
- 不鮮明、見切れ、ページ不足の場合は`判定不能`とする。
- 学生の意図を根拠なく推測しない。
- SWOTの正確性や戦略の良し悪しは点数に反映しない。

## 6. 作業点

最初にP1～P3をすべて判定し、その後で`Yes`の個数から作業点を機械的に決定する。

| Yesの個数 | 作業点 |
|---:|---:|
| 3個 | 2点 |
| 1個または2個 | 1点 |
| 0個かつP1～P3がすべてNo | 0点 |

- 提出物がない場合は0点とする。ただし、提出なしはVLMではなく、`grader.py`の提出物走査処理で判定する。
- 内容の質を理由に作業点を下げない。

## 7. 判定不能の処理

`判定不能`を`No`として扱わない。

P1～P3に`判定不能`が1つ以上ある場合は、次の順序で処理する。

1. `Yes`と確認できた項目数だけで暫定作業点を計算する。
2. `暫定点`を`true`にする。
3. `人間確認必要`を`true`にする。
4. 判断できなかった項目名と理由を`人間確認理由`に記載する。

`Yes`が0個で、1項目以上が`判定不能`の場合、暫定作業点は0点とする。人間確認後に点数が上がる可能性があることを`評価理由`に記載する。

例：P1=`Yes`、P2=`判定不能`、P3=`No`の場合、暫定作業点は1点とし、人間確認後に2点へ変更される可能性がある。

## 8. PDF形式

提出形式は答案画像からVLMに推測させない。将来的に`grader.py`が、採点対象となった元ファイルの拡張子から判定する。

- PDF：`PDF形式減点`は0
- PDF以外：`PDF形式減点`は-1
- 提出なし：`点数`は0
- 遅延：減点なし

元ファイル形式がプロンプト等で明示されていない場合、VLMは形式を推測せず、`PDF形式減点`を暫定的に0とする。形式確認が必要であることを`人間確認理由`に記載し、`暫定点`と`人間確認必要`をともに`true`にする。

```text
点数 = max(0, 作業点 + PDF形式減点)
```

## 9. フィードバック

プレ課題では、不足している作業を簡潔に伝える。内容の正確性や完成度は点数に反映しない。最終課題へ向けた参考として、画像から明確に確認できる不足を1つだけ記載してもよい。

使用できる例：

- 「SWOT分析、取り得る戦略、方向性の提案の3つへの取組が確認できました。」
- 「強み、弱み、機会、脅威の4つの観点で現状を整理してください。」
- 「SWOT分析の要素を組み合わせて、取り得る戦略を作成してください。」
- 「分析結果を踏まえ、企画をどの方向へ進めるか文章で提案してください。」
- 「PDF形式で提出してください。」

判定不能の項目を「存在しない」と断定しない。

## 10. 出力JSONテンプレート

説明文、前置き、Markdownのコードブロックを付けず、次のキーを一字一句変えずにJSONだけを返すこと。

```json
{
  "点数": 2,
  "暫定点": false,
  "観察項目": {
    "P1_SWOT分析への取組": "Yes",
    "P2_取り得る戦略の作成": "Yes",
    "P3_明確な方向性の提案": "Yes"
  },
  "観点別評価": {
    "取組状況": "SWOT分析、取り得る戦略、方向性の提案への取組が確認できる",
    "提出形式": "PDF形式で提出されている"
  },
  "配点内訳": {
    "作業点": 2,
    "PDF形式減点": 0
  },
  "減点理由": [],
  "評価理由": "指定された3種類の作業すべてへの取組が確認されたため、作業点は2点",
  "フィードバック": "",
  "人間確認必要": false,
  "人間確認理由": []
}
```

## 11. JSONの制約

- `点数`は0、1、2のいずれかとする。
- `暫定点`と`人間確認必要`はJSONのbooleanとし、文字列にしない。
- P1～P3は`Yes`、`No`、`判定不能`のいずれかとする。
- `Partial`は使用しない。
- `作業点`は0、1、2のいずれかとする。
- `PDF形式減点`は0または-1とする。
- `点数`は`max(0, 作業点 + PDF形式減点)`と一致させる。
- 提出なしは0点とする。
- P1～P3に判定不能が1つでもあれば`暫定点=true`、`人間確認必要=true`とする。
- 元ファイル形式が確定していない場合も`暫定点=true`、`人間確認必要=true`とする。
- `人間確認必要=true`なら`人間確認理由`を空配列にしない。
- 遅延による減点項目を作らない。
- 教え合いを採点項目に含めない。
- 内容の良し悪しを点数へ反映しない。
- 同じ不足を重複して減点しない。
- 失点またはPDF形式減点がある場合は、該当項目と理由を`減点理由`に記載する。
- `評価理由`には、`Yes`の個数、作業点、PDF形式減点、最終点の計算を記載する。
