# 第6回課題（プレ）評価計画：採点基準

## 1. 課題内容

大学祭における出店企画について、これまでに作成した目的展開、ニーズ展開、SWOT分析、戦略および方向性を踏まえて、企画を評価するための計画を作成する。

プレ提出で確認する作業は次の4種類である。

1. 大学祭出店の目標を文章化する
2. 目標を達成するための全体機能を提示する
3. 全体機能を評価するため、QCDの観点から評価項目を列挙する
4. 列挙した評価項目を使って、妥当性確認用の評価展開図を作成する

課題文の（5）にある教え合いの記録は、プレ提出の点数に含めない。

## 2. 採点方針

このプレ課題は2点満点とする。内容の良し悪し、評価項目の適切さ、項目数、図の完成度、見た目、文章表現は点数に使用せず、指定された4種類の作業に取り組んでいるかを評価する。

- 4種類すべてに取り組んでいる：2点
- 1～3種類に取り組んでいる：1点
- 4種類とも確認できない：0点
- 提出なし：0点
- PDF以外：作業点から1点減点
- 遅延：減点なし

最終点は次の式で計算する。

```text
点数 = max(0, 作業点 + PDF形式減点)
```

## 3. 判定値

観察項目には次の値だけを使用する。`Partial`は使用しない。

- `Yes`：該当する作業に取り組んだ形跡が確認できる
- `No`：該当する作業の形跡が確認できない
- `判定不能`：不鮮明、見切れ、ページ不足などで判断できない

## 4. 観察項目

- P1_目標の文章化への取組
- P2_全体機能の提示
- P3_QCD評価項目の列挙
- P4_評価展開図への取組

## 5. P1_目標の文章化への取組

課題では、文章化した目標に次の内容を含めるよう指示されている。

- 狙いと背景
- 完成時のイメージまたはシナリオ
- 具体的な目的と効果

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「目標」「狙いと背景」「完成時のイメージ」「目的と効果」などの見出しと文章がある
- 出店企画で何を実現したいかが文章で書かれている
- 完成時にどのような体験や状態を実現したいかが書かれている
- 狙い、背景、目的、効果の一部が不足していても、目標を文章化しようとした形跡がある

プレ課題では、次の問題があっても取組が確認できれば`Yes`とする。

- 狙いと背景が短い
- シナリオが抽象的
- 目的と効果の一方が不足している
- 来場者または出店者の一方に偏っている
- 箇条書きが含まれている
- 文章表現が不十分

### Noまたは判定不能とする条件

- 「目標」という見出しだけで内容がない：`No`
- 企画名だけで、実現したい状態が全く書かれていない：`No`
- 課題と無関係な文章しかない：`No`
- 不鮮明、見切れ、ページ不足により文章を確認できない：`判定不能`

## 6. P2_全体機能の提示

全体機能とは、文章化した目標を実現するために、企画やシステム全体が果たすべき働きである。製品名や設備名そのものではなく、企画が「何をするか」「どのような働きを提供するか」を表す。

例：

- 来場者へ混雑状況を伝える
- 来場者と出店者の交流を促す
- 待ち時間を管理する
- 安全に来場者を誘導する
- 記憶に残る体験を提供する

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「全体機能」という見出しと内容がある
- 目標を実現するために必要な働きが列挙されている
- 文章、表、箇条書き、図などで複数の機能が示されている
- 「機能」という語がなくても、企画が提供すべき働きを整理した記載がある

プレ課題では、次の問題があっても取組が確認できれば`Yes`とする。

- 全体機能の数が少ない
- 機能と具体的手段が一部混在している
- 目標とのつながりが弱い
- 機能の表現が抽象的
- 階層化されていない

### Noまたは判定不能とする条件

- 「全体機能」という見出しだけで内容がない：`No`
- 商品名、設備名、アプリ名などだけがあり、働きを読み取れない：`No`
- 目標の文章を再掲しただけで、機能を示していない：`No`
- 何が全体機能に該当するか、画像不足等により判断できない：`判定不能`

## 7. P3_QCD評価項目の列挙

QCDは、企画、製品、サービスなどを評価する代表的な3つの観点である。

- Q：Quality／品質
- C：Cost／費用・コスト
- D：Delivery／納期・時間・提供時期

この課題では、全体機能を評価するための項目をQ・C・Dの観点から考える。評価項目とは「企画や機能の良し悪しを何によって確認するか」を示す項目である。

例：

- Q／品質：来場者の満足度、安全性、情報の分かりやすさ、待ち時間の短縮効果
- C／費用：必要経費、1人当たりの提供費用、人員数、設備費
- D／納期・時間：準備に必要な期間、提供までの時間、待ち時間、作業完了予定日

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- Q・C・Dの見出しと評価項目がある
- 品質、費用、納期または時間の3観点から項目が列挙されている
- 表、文章、箇条書きなどで、全体機能を評価する項目が示されている
- QCDの一部が不足していても、QCDを使って評価項目を考えた形跡がある

プレ課題では、次の問題があっても取組が確認できれば`Yes`とする。

- Q・C・Dの一部しかない
- 評価項目の数が少ない
- 評価項目と目標の関係が不明確
- 測定方法が書かれていない
- 定量的な基準がない
- Q・C・Dの分類に誤りがある
- 納期が課題文の想定日と異なる

課題文には納期を「2027年度大宮祭開催日」と想定するとあるが、日付の正しさはプレ課題の点数に使用しない。

### Noまたは判定不能とする条件

- QCDという見出しだけで項目がない：`No`
- 全体機能を再掲しただけで、評価する観点や項目がない：`No`
- Q・C・Dと無関係な感想だけがある：`No`
- 不鮮明、見切れ、ページ不足により項目を確認できない：`判定不能`

## 8. P4_評価展開図への取組

評価展開図とは、企画の目標、全体機能、QCDによる評価項目などの関係を整理し、何をどの観点で評価するかを確認するための図である。この課題では、列挙した評価項目を使い、全体機能や目標を適切に評価できるか確認する目的で作成する。

図の形式は一つに限定せず、次のような形式を認める。

- 目標、機能、評価項目を階層的に結んだ図
- 全体機能と評価項目の対応を線で示した図
- 行列や表によって機能と評価項目の対応を示したもの
- Q・C・Dごとの評価項目を全体機能へ対応付けた図

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「評価展開図」という見出しと図がある
- 全体機能と評価項目が線、配置、表などで関連付けられている
- 目標、機能、評価項目の対応関係を整理しようとした図がある
- 一般的な見本と形式が異なっていても、評価項目の対応を図示しようとした形跡がある

プレ課題では、次の問題があっても取組が確認できれば`Yes`とする。

- 一部の評価項目が図に反映されていない
- 全体機能との対応が一部不明確
- 線が不足している
- 階層や配置に改善の余地がある
- Q・C・Dの区分が一部不明確
- 評価項目の妥当性が十分に検証されていない
- 図が簡略化されている

### Noまたは判定不能とする条件

- 「評価展開図」という見出しだけで図がない：`No`
- 評価項目を単に列挙しただけで、機能等との対応を示していない：`No`
- 課題と無関係な図しかない：`No`
- 図はあるが、画像不足等により評価展開図への取組か判断できない：`判定不能`

## 9. 誤判定防止

- 同じ記載を、根拠なくP1～P4すべてに数えない。
- P1は、目標を文章で示す作業を確認する。
- P2は、目標を実現するための働きを示す作業を確認する。
- P3は、QCDから評価項目を列挙する作業を確認する。
- P4は、機能と評価項目の対応関係を図示する作業を確認する。
- 内容が不十分でも、該当作業への取組があれば`Yes`とする。
- 見出しだけで内容がなければ`No`とする。
- 不鮮明、見切れ、ページ不足の場合は`判定不能`とする。
- 学生の意図を根拠なく推測しない。
- 内容の正確性や完成度はプレ課題の点数に反映しない。

## 10. 作業点

P1～P4の`Yes`の数から、作業点を機械的に決定する。

- `Yes`が4個：2点
- `Yes`が1～3個：1点
- `Yes`が0個で、すべて`No`：0点
- 提出物なし：0点

内容の良し悪しを理由に作業点を下げない。

## 11. 判定不能の処理

`判定不能`を`No`として扱わない。判定不能がある場合は次のように処理する。

1. `Yes`と確認できた項目数だけで暫定作業点を計算する
2. `暫定点=true`とする
3. `人間確認必要=true`とする
4. 判断できなかった観察項目名と理由を`人間確認理由`に記載する

例：P1=`Yes`、P2=`Yes`、P3=`判定不能`、P4=`No`の場合、`Yes`は2個なので暫定作業点は1点とする。人間確認後に2点へ変更される可能性がある。

## 12. PDF形式

従来のプレ課題の規則に従う。

- PDF：`PDF形式減点=0`
- PDF以外：`PDF形式減点=-1`
- 提出なし：`点数=0`
- 遅延：減点なし

提出形式は答案画像からVLMに推測させない。将来的に`grader.py`が、実際に採点対象として選択した元ファイルの拡張子から判定する。今回は`grader.py`を変更しない。

元ファイル形式がPython側から与えられていない場合、VLMは形式を推測せず、形式確認が必要であることを示す。

## 13. フィードバック

プレ課題では、不足している作業を簡潔に伝える。内容の正確性や完成度は点数に反映しない。最終課題へ向けた参考として、明らかな不足を一つだけフィードバックに記載してもよい。

使用できる例：

- 「目標の文章化、全体機能、QCD評価項目、評価展開図の4つへの取組が確認できました。」
- 「狙いと背景、完成時のイメージ、具体的な目的と効果を含めて目標を文章化してください。」
- 「目標を実現するために、企画全体が果たす機能を記載してください。」
- 「品質、費用、納期・時間の観点から評価項目を列挙してください。」
- 「全体機能と評価項目の対応が分かる評価展開図を作成してください。」
- 「PDF形式で提出してください。」

## 14. 出力JSON

説明文やMarkdownのコードブロックを付けず、次の構造のJSONだけを返す。

```json
{
  "点数": 2,
  "暫定点": false,
  "観察項目": {
    "P1_目標の文章化への取組": "Yes",
    "P2_全体機能の提示": "Yes",
    "P3_QCD評価項目の列挙": "Yes",
    "P4_評価展開図への取組": "Yes"
  },
  "観点別評価": {
    "取組状況": "目標の文章化、全体機能、QCD評価項目、評価展開図への取組が確認できる",
    "提出形式": "PDF形式で提出されている"
  },
  "配点内訳": {

  "人間確認理由": []
}
```

## 15. JSONの制約

- `点数`は0、1、2のいずれかとする。
- `暫定点`と`人間確認必要`はJSONのbooleanとし、文字列にしない。
- P1～P4は`Yes`、`No`、`判定不能`のいずれかとする。
- `Partial`は使用しない。
- `作業点`は0、1、2のいずれかとする。
- `PDF形式減点`は0または-1とする。
- `点数`は`max(0, 作業点 + PDF形式減点)`と一致させる。
- 提出なしは0点とする。
- 判定不能が1つでもあれば`暫定点=true`とする。
- 判定不能が1つでもあれば`人間確認必要=true`とする。
- `人間確認必要=true`の場合は`人間確認理由`を空にしない。
- 遅延による減点項目を作らない。
- 教え合いを採点項目に含めない。
- 内容の良し悪しを点数へ反映しない。
- 同じ不足を重複して減点しない。
