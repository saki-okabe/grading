# 第7回課題（プレ）QFD：採点基準

## 1. 課題内容

大学祭における出店企画について、目標を明確化した後、QFDを用いて要求品質を整理し、重点的に担保すべき質を検討する。

プレ提出で確認する作業は次の3種類である。

1. 文章化された目標を達成するための全体機能を、要求品質の1次項目へ変換する
2. 要求品質を3次項目まで展開し、品質要素との対応を示す品質展開表を作成する
3. 品質展開表から重点項目を決め、担保すべき質を記述する

課題文の（4）にある教え合いの記録は、プレ提出の点数に含めない。

## 2. 採点方針

このプレ課題は2点満点とする。内容の良し悪し、QFDの正確性、項目数、計算の正確性、表の完成度、見た目は点数に使用せず、指定された3種類の作業に取り組んでいるかを評価する。

- 3種類すべてに取り組んでいる：2点
- 1種類または2種類に取り組んでいる：1点
- 3種類とも確認できない：0点
- 提出なし：0点
- PDF以外：作業点から1点減点
- 遅延：減点なし

```text
点数 = max(0, 作業点 + PDF形式減点)
```

## 3. QFDに関する用語

### QFD

QFDは、利用者や関係者が求めることを、企画、製品、サービスに必要な品質や機能へ展開し、何を重点的に実現するかを整理する方法である。この課題では次の流れを確認する。

```text
全体機能
→ 要求品質
→ 1次・2次・3次への展開
→ 品質要素との対応
→ 重点項目
→ 担保すべき質
```

### 要求品質

要求品質とは、利用者や関係者が企画、製品、サービスに求める性質や状態である。課題では全体機能を「名詞＋動詞＋修飾語」の形へ変換するよう指示されている。

表現例：

- 情報を分かりやすく伝える
- 待ち時間を短くする
- 商品を安全に提供する
- 来場者を円滑に誘導する
- 出店者が状況を容易に把握できる

表現が完全にこの語順でなくても、要求される状態や質として読めれば取組として認める。

### 要求品質の階層

- 1次項目：要求品質を大きくまとめた上位項目
- 2次項目：1次項目を具体化した中位項目
- 3次項目：評価や設計へ使える程度まで具体化した下位項目

階層が下がるほど、要求品質の内容が具体的になる。

### 品質要素

品質要素とは、要求品質を実現するために、企画やサービス側で設計、測定、管理する品質上の特性である。

例：情報の表示時間、待ち時間、誘導表示の文字サイズ、誤案内の発生件数、提供に要する時間、必要人員数、利用者満足度。

### 品質展開表

品質展開表とは、要求品質と品質要素の対応関係を行列や表によって整理したものである。一般的には次の内容を含む。

- 行または列に要求品質
- 反対側に品質要素
- 要求品質と品質要素の関係の強さ
- 必要に応じて重要度、重み、評価値、重点度など

## 4. 判定値と観察項目

観察項目には次の値だけを使用し、`Partial`は使用しない。

- `Yes`：該当する作業に取り組んだ形跡が確認できる
- `No`：該当する作業の形跡が確認できない
- `判定不能`：不鮮明、見切れ、ページ不足などで判断できない

観察項目：

- P1_全体機能から要求品質への変換
- P2_要求品質の展開と品質展開表
- P3_重点項目と担保すべき質

## 5. P1_全体機能から要求品質への変換

文章化した目標を達成するための全体機能を、要求品質の1次項目へ変換する作業を確認する。

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「要求品質」「要求品質1次」「1次項目」などの見出しと項目がある
- 全体機能を、求められる状態や質を表す文章へ変換している
- 「名詞＋動詞＋修飾語」を意識した要求品質の表現がある
- 全体機能と要求品質1次項目の対応を表、線、番号、配置などで示している
- 対応関係は明記されていなくても、要求品質の1次項目を作ろうとした形跡がある

次の問題があっても、取組が確認できれば`Yes`とする。

- 「名詞＋動詞＋修飾語」の形が一部崩れている
- 修飾語が不足している
- 全体機能と要求品質がほぼ同じ表現である
- 要求品質の項目数が少ない
- 一部に具体的な手段や設備名が混ざっている
- 全体機能との対応が不明確

### Noまたは判定不能とする条件

- 「要求品質」という見出しだけで項目がない：`No`
- 全体機能を記載しただけで、要求品質へ変換した形跡がない：`No`
- 商品名、設備名、アプリ名などの具体策だけが並んでいる：`No`
- 課題と無関係な記載しかない：`No`
- 不鮮明、見切れ、ページ不足により項目を確認できない：`判定不能`

## 6. P2_要求品質の展開と品質展開表

要求品質を1次項目から2次項目、3次項目へ具体化し、品質要素との対応を示す品質展開表を作成する作業を確認する。

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 要求品質の1次、2次、3次項目が表や図で示されている
- 要求品質が複数段階へ展開されている
- 「品質展開表」という見出しと表がある
- 要求品質と品質要素を行と列へ配置した表がある
- 要求品質と品質要素の関係を記号、数値、色、印などで示している
- 階層や表が不完全でも、要求品質を展開して品質要素へ対応付けようとした形跡がある

次の問題があっても、取組が確認できれば`Yes`とする。

- 3次項目まで完全に展開されていない
- 一部の項目だけ2次または3次へ展開されている
- 要求品質と品質要素の区別に誤りがある
- 関係記号の使い方が一部不明確
- 関係の強さが定量化されていない
- 重要度や重みが記載されていない
- 表の一部が空欄
- 項目数が少ない
- 品質展開表の形式が見本と異なる

### Noまたは判定不能とする条件

- 見出しだけで表や図がない：`No`
- 要求品質を単に列挙しただけで、展開や品質要素との対応がない：`No`
- 品質要素だけがあり、要求品質との対応を示していない：`No`
- 課題と無関係な表しかない：`No`
- 表はあるが、画像不足等により品質展開表への取組か判断できない：`判定不能`

## 7. P3_重点項目と担保すべき質

重点項目とは、品質展開表の結果から、特に重視すべき要求品質または品質要素として選んだ項目である。担保すべき質とは、その重点項目について、企画が必ず満たすべき品質、状態、性能などを文章で説明したものである。

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「重点項目」「重点品質」「重要項目」などの見出しと項目がある
- 品質展開表の中から、重視する要求品質または品質要素を選んでいる
- 「担保すべき質」という見出しと説明がある
- 重点項目について、何を満たすべきか文章で述べている
- 選定理由が不十分でも、重点項目を決めて担保すべき質を述べようとした形跡がある

次の問題があっても、取組が確認できれば`Yes`とする。

- 重点項目が1つだけ
- 選定理由がない
- 計算によって重点項目を決めていない
- 品質展開表との対応が弱い
- 担保すべき質が抽象的
- 数値目標がない
- 重点項目と担保すべき質の対応が一部不明確

### Noまたは判定不能とする条件

- 「重点項目」という見出しだけで内容がない：`No`
- 品質展開表はあるが、重点項目を選んでいない：`No`
- 重点項目だけで、担保すべき質について何も述べていない：`No`
- 単なる感想や企画の宣伝文だけである：`No`
- 不鮮明、見切れ、ページ不足により内容を確認できない：`判定不能`

## 8. 誤判定防止

- 同じ表だけを、根拠なくP1～P3すべてに数えない。
- P1は、全体機能から要求品質1次項目への変換を確認する。
- P2は、要求品質の階層展開と品質要素との対応表を確認する。
- P3は、重点項目の選定と担保すべき質の記述を確認する。
- 内容に誤りがあっても、該当作業への取組があれば`Yes`とする。
- 見出しだけで内容がなければ`No`とする。
- 不鮮明、見切れ、ページ不足の場合は`判定不能`とする。
- 学生の意図を根拠なく推測しない。
- 内容の正確性、計算の正確性、完成度はプレ課題の点数に反映しない。

## 9. 作業点

P1～P3の`Yes`の数から、作業点を機械的に決定する。

- `Yes`が3個：2点
- `Yes`が1個または2個：1点
- `Yes`が0個で、すべて`No`：0点
- 提出物なし：0点

内容の良し悪しを理由に作業点を下げない。

## 10. 判定不能の処理

`判定不能`を`No`として扱わない。判定不能がある場合は次のように処理する。

1. `Yes`と確認できた項目数だけで暫定作業点を計算する
2. `暫定点=true`とする
3. `人間確認必要=true`とする
4. 判断できなかった観察項目名と理由を`人間確認理由`に記載する

例：P1=`Yes`、P2=`判定不能`、P3=`No`の場合、`Yes`は1個なので暫定作業点は1点とする。人間確認後に2点へ変更される可能性がある。

## 11. PDF形式

従来のプレ課題の規則に従う。

- PDF：`PDF形式減点=0`
- PDF以外：`PDF形式減点=-1`
- 提出なし：`点数=0`
- 遅延：減点なし

提出形式は答案画像からVLMに推測させない。将来的に`grader.py`が、実際に採点対象として選択した元ファイルの拡張子から判定する。今回は`grader.py`を変更しない。

## 12. フィードバック

プレ課題では、不足している作業を簡潔に伝える。内容の正確性や完成度は点数に反映しない。最終課題へ向けた参考として、明らかな不足を一つだけフィードバックに記載してもよい。

使用できる例：

- 「要求品質への変換、品質展開表、重点項目と担保すべき質の3つへの取組が確認できました。」
- 「全体機能を、求められる状態や質を表す要求品質へ変換してください。」
- 「要求品質を1次、2次、3次へ具体化してください。」
- 「要求品質と品質要素の対応を示す品質展開表を作成してください。」
- 「品質展開表から重点項目を選び、担保すべき質を文章で述べてください。」
- 「PDF形式で提出してください。」

## 13. 出力JSON

説明文やMarkdownのコードブロックを付けず、次の構造のJSONだけを返す。

```json
{
  "点数": 2,
  "暫定点": false,
  "観察項目": {
    "P1_全体機能から要求品質への変換": "Yes",
    "P2_要求品質の展開と品質展開表": "Yes",
    "P3_重点項目と担保すべき質": "Yes"
  },
  "観点別評価": {
    "取組状況": "要求品質への変換、品質展開表、重点項目と担保すべき質への取組が確認できる",
    "提出形式": "PDF形式で提出されている"
  },
  "配点内訳": {
    "作業点": 2,
    "PDF形式減点": 0
  },
  "減点理由": [],
  "評価理由": "指定された3種類の作業すべてへの取組が確認されたため、作業点は2点",
  "フィードバック": "",

  "人間確認理由": []
}
```

## 14. JSONの制約

- `点数`は0、1、2のいずれかとする。
- `暫定点`と`人間確認必要`はJSONのbooleanとし、文字列にしない。
- P1～P3は`Yes`、`No`、`判定不能`のいずれかとする。
- `Partial`は使用しない。
- `作業点`は0、1、2のいずれかとする。
- `PDF形式減点`は0または-1とする。
- `点数`は`max(0, 作業点 + PDF形式減点)`と一致させる。
- 提出なしは0点とする。
- 判定不能が1つでもあれば`暫定点=true`とする。
- 判定不能が1つでもあれば`人間確認必要=true`とする。
- `人間確認必要=true`の場合は`人間確認理由`を空にしない。
- 遅延による減点項目を作らない。
- 教え合いを採点項目に含めない。
- 内容や計算の良し悪しを点数へ反映しない。
- 同じ不足を重複して減点しない。
