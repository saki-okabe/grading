# 第8回課題（プレ）代替案の設計

## 1. 課題内容

大学祭における出店企画について、これまでに作成した目標、全体機能、要求品質、品質要素、品質展開表および重点項目を踏まえ、具体的な代替案を提案する。

課題の主目的は、次のとおりである。

> 来場者と出店者の双方にとって、記憶に残る大学祭体験を創出すること

プレ提出で確認する作業は次の3種類である。

1. 品質要素の重点項目、すなわち担保すべき質を考慮する
2. 目標を実現するための代替案を提案する
3. その代替案を提案した理由を、できるだけ詳しく説明する

課題文の（2）にある教え合いの記録は、プレ提出の点数に含めない。

## 2. 採点方針

このプレ課題は2点満点とする。代替案の優劣、独創性、実現可能性、文章量、図の完成度、見た目は点数に使用せず、指定された次の3種類の作業に取り組んでいるかを評価する。

- P1_代替案の提案
- P2_重点項目または担保すべき質の考慮
- P3_代替案を提案した理由の説明

点数は次のように決定する。

- P1～P3の3つすべてが`Yes`：2点
- `Yes`が1個または2個：1点
- すべて`No`：0点
- 提出なし：0点
- PDF以外：作業点から1点減点
- 遅延：減点なし

```text
点数 = max(0, 作業点 + PDF形式減点)
```

## 3. 用語の定義

### 代替案

代替案とは、目標を実現するために考えられる、具体的な企画、仕組み、サービス、運営方法などの候補である。

「代替」という言葉は、必ずしも既存案を否定する意味ではない。目標を実現するために比較・検討できる設計案や企画案を指す。

代替案の例：

- 整理券による待ち時間管理
- スマートフォンでの順番通知
- 会場内の混雑表示
- 来場者参加型の体験企画
- 出店者と来場者が交流する仕組み
- 複数の提供方法や運営方法

この例と完全に一致する必要はない。

### 重点項目

重点項目とは、前回の品質展開表の計算結果などから、特に重視すべきものとして選んだ要求品質または品質要素である。

### 担保すべき質

担保すべき質とは、重点項目について、企画が必ず満たすべき品質、状態、性能などである。

例：

- 待ち時間を一定時間以内にする
- 来場者が情報を容易に理解できる
- 商品を安全に提供できる
- 出店者の作業負担を抑える
- 混雑時にも安定して運営できる

## 4. 判定値と観察項目

観察項目には次の値だけを使用し、`Partial`は使用しない。

- `Yes`：該当する作業に取り組んだ形跡が確認できる
- `No`：該当する作業の形跡が確認できない
- `判定不能`：不鮮明、見切れ、ページ不足などで判断できない

観察項目：

- P1_代替案の提案
- P2_重点項目または担保すべき質の考慮
- P3_代替案を提案した理由の説明

## 5. P1_代替案の提案

目標を実現するための具体的な企画、仕組み、サービスまたは運営方法が提案されているかを確認する。

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「代替案」「提案」「企画案」「設計案」などの見出しと具体的な内容がある
- 目標を実現するための企画、仕組み、サービスまたは運営方法が提案されている
- 図、文章、表、箇条書きなどで、実施しようとする案が示されている
- 代替案という語がなくても、具体的な提案内容を読み取れる
- 案が1つだけでも、具体的な提案として成立している

次の問題があっても、取組が確認できれば`Yes`とする。

- 代替案が1つだけ
- 提案が抽象的
- 実現可能性に疑問がある
- 詳細な仕組みが書かれていない
- 図がない
- 既存のアイデアと似ている
- 代替案同士を比較していない
- 企画の独創性が低い

### Noまたは判定不能とする条件

- 「代替案」という見出しだけで内容がない：`No`
- 目標や重点項目を再掲しただけで、実施する案がない：`No`
- 「楽しくする」「成功させる」などの抽象的な目標だけである：`No`
- 課題と無関係な案しかない：`No`
- 不鮮明で提案内容を確認できない：`判定不能`

## 6. P2_重点項目または担保すべき質の考慮

品質要素の重点項目または担保すべき質を考慮して代替案を検討しているかを確認する。

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「重点項目」「重要項目」「担保すべき質」などが明記されている
- 前回のQFDまたは品質展開表で決めた重点項目を記載している
- 代替案がどの重点項目へ対応するか説明している
- 代替案によって、どの質を満たすか説明している
- 重点項目という語がなくても、安全性、待ち時間、分かりやすさなど、重視する質と代替案の関係が明確である

次の問題があっても、取組が確認できれば`Yes`とする。

- 重点項目が1つだけ
- QFDの計算結果を再掲していない
- 数値目標がない
- 重点項目と担保すべき質の区別が不明確
- 対応関係の説明が短い
- 前回の品質展開表との完全な一致を確認できない

### Noまたは判定不能とする条件

- 重点項目または担保すべき質に全く触れていない：`No`
- 代替案だけがあり、何の質を重視した案なのか分からない：`No`
- 品質と無関係な感想だけがある：`No`
- 重点項目の記載が不鮮明で確認できない：`判定不能`

## 7. P3_代替案を提案した理由の説明

なぜその代替案を提案したのか、その理由、目標との関係または期待する効果が説明されているかを確認する。

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「理由」「提案理由」「選定理由」などの見出しと文章がある
- なぜその代替案が目標の実現に有効か説明している
- なぜその代替案が重点項目または担保すべき質に対応できるか説明している
- 代替案を実施することで、誰にどのような効果があるか説明している
- 明確な見出しがなくても、代替案を選んだ理由を文章から読み取れる

次の問題があっても、取組が確認できれば`Yes`とする。

- 理由が短い
- 根拠となる数値がない
- 説明が抽象的
- 来場者または出店者の一方に偏っている
- 重点項目とのつながりが弱い
- 他案との比較がない
- 理由の妥当性に疑問がある

### Noまたは判定不能とする条件

- 理由の記載がない：`No`
- 「良いと思ったから」「楽しそうだから」などの感想だけで、案の効果や目的との関係を読み取れない：`No`
- 代替案の内容を繰り返しただけで、なぜ採用するか説明していない：`No`
- 重点項目や目標を再掲しただけで、代替案との関係を説明していない：`No`
- 文章が不鮮明で理由を確認できない：`判定不能`

## 8. 誤判定防止

- 同じ文章を、根拠なくP1～P3すべてに数えない。
- P1では、実施する具体的な案があるか確認する。
- P2では、重点項目または担保すべき質を考慮しているか確認する。
- P3では、なぜその案を提案したか説明しているか確認する。
- 内容が不十分でも、該当作業への取組があれば`Yes`とする。
- 見出しだけで内容がなければ`No`とする。
- 不鮮明、見切れ、ページ不足は`判定不能`とする。
- 学生の意図を根拠なく推測しない。
- 代替案の良し悪し、独創性、実現可能性を点数へ反映しない。

## 9. 作業点

P1～P3の`Yes`の数から、作業点を機械的に決定する。

- `Yes`が3個：2点
- `Yes`が1個または2個：1点
- `Yes`が0個で、すべて`No`：0点
- 提出物なし：0点

内容の良し悪しを理由に作業点を下げない。

## 10. 判定不能の処理

`判定不能`を`No`として扱わない。判定不能がある場合は次のように処理する。

1. `Yes`と確認できた項目数だけで暫定作業点を計算する
2. `暫定点=true`とする
3. `人間確認必要=true`とする
4. 判定できなかった観察項目名と理由を`人間確認理由`に記載する

例：P1=`Yes`、P2=`判定不能`、P3=`No`の場合、`Yes`は1個なので暫定作業点は1点とする。人間確認後に2点へ変更される可能性がある。

## 11. PDF形式

従来のプレ課題の規則に従う。

- PDF：`PDF形式減点=0`
- PDF以外：`PDF形式減点=-1`
- 提出なし：`点数=0`
- 遅延：減点なし

提出形式はVLMに推測させない。将来的に`grader.py`が、採点対象となった元ファイルの拡張子から判定する。今回は`grader.py`を変更しない。

## 12. フィードバック

プレ課題では、不足している作業を簡潔に伝える。内容の正確性や完成度は点数に反映しない。最終課題へ向けた参考として、明らかな不足を一つだけフィードバックへ記載してもよい。

使用できる例：

- 「代替案、重点項目との関係、提案理由の3つへの取組が確認できました。」
- 「目標を実現するための具体的な代替案を提案してください。」
- 「品質展開表で選んだ重点項目または担保すべき質を明記してください。」
- 「代替案によって、どの重点項目や質へ対応するのか説明してください。」
- 「なぜその代替案を提案するのか、目標や期待する効果と結び付けて説明してください。」
- 「PDF形式で提出してください。」

## 13. 出力JSON

説明文やMarkdownのコードブロックを付けず、次の構造のJSONだけを返す。

```json
{
  "点数": 2,
  "暫定点": false,
  "観察項目": {
    "P1_代替案の提案": "Yes",
    "P2_重点項目または担保すべき質の考慮": "Yes",
    "P3_代替案を提案した理由の説明": "Yes"
  },
  "観点別評価": {
    "取組状況": "代替案、重点項目との関係、提案理由への取組が確認できる",
    "提出形式": "PDF形式で提出されている"
  },
  "配点内訳": {
    "作業点": 2,
    "PDF形式減点": 0
  },
  "減点理由": [],
  "評価理由": "指定された3種類の作業すべてへの取組が確認されたため、作業点は2点",
  "フィードバック": "",
  "人間確認必要": false,
  "人間確認理由": []
}
```

## 14. JSONの制約

- `点数`は0、1、2のいずれかとする。
- `暫定点`と`人間確認必要`はJSONのbooleanとし、文字列にしない。
- P1～P3は`Yes`、`No`、`判定不能`のいずれかとする。
- `Partial`は使用しない。
- `作業点`は0、1、2のいずれかとする。
- `PDF形式減点`は0または-1とする。
- `点数`は`max(0, 作業点 + PDF形式減点)`と一致させる。
- 提出なしは0点とする。
- 判定不能が1つでもあれば`暫定点=true`とする。
- 判定不能が1つでもあれば`人間確認必要=true`とする。
- `人間確認必要=true`の場合は`人間確認理由`を空にしない。
- 遅延による減点項目を作らない。
- 教え合いを採点項目に含めない。
- 内容の良し悪しを点数へ反映しない。
- 同じ不足を重複して減点しない。
