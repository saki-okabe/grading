# 第9回課題（プレ）評価法

## 1. 課題内容

大学祭における出店企画について、これまでに提案した代替案を関連マトリクス法で評価し、その評価表を選んだ理由を説明する。

課題の主目的は、次のとおりである。

> 来場者と出店者の双方にとって、記憶に残る大学祭体験を創出すること

プレ提出で確認する作業は次の3種類である。

1. 提案した代替案を、関連マトリクス法を用いて評価する
2. 評価者の視点を設定し、評価項目へ重みを付ける
3. 作成した評価表を選択した理由を説明する

課題文の（3）にある教え合いの記録は、プレ提出の点数に含めない。

## 2. 採点方針

このプレ課題は2点満点とする。評価結果の正しさ、評価項目の良し悪し、重みの妥当性、計算の正確性、選ばれた案の優劣、表の見た目は点数に使用せず、指定された次の3種類の作業に取り組んでいるかを評価する。

- P1_関連マトリクスによる評価
- P2_評価者と重み付けの設定
- P3_評価表を選択した理由の説明

点数は次のように決定する。

- P1～P3の3つすべてが`Yes`：2点
- `Yes`が1個または2個：1点
- すべて`No`：0点
- 提出なし：0点
- PDF以外：作業点から1点減点
- 遅延：減点なし

```text
点数 = max(0, 作業点 + PDF形式減点)
```

## 3. 用語の定義

### 関連マトリクス法

関連マトリクス法とは、複数の代替案を複数の評価項目で比較する方法である。

一般的には表の中に次の内容を配置する。

- 比較する代替案
- 評価項目
- 各評価項目の重み
- 各代替案に対する評価値
- 必要に応じて、評価値と重みを使った得点
- 必要に応じて、合計点や順位

表の行と列は逆でもよい。

### 評価項目

評価項目とは、代替案の良し悪しを比較する観点である。

課題では、教科書7.2節に示される評価項目から6項目以上を使用するよう指示されている。具体的な評価項目名は提出物に従って確認する。

評価項目の例：

- 効果
- 品質
- 安全性
- 利便性
- 実現可能性
- 費用
- 準備期間
- 運営負担
- 来場者満足
- 出店者への効果

この例と完全に一致する必要はない。

### 評価者

評価者とは、どの立場・視点から代替案を評価するかを示すものである。

例：

- 来場者
- 出店者
- 大学祭運営者
- 学生
- 教職員
- 安全管理担当者

### 重み

重みとは、評価者の立場から見た評価項目の重要さを示す数値である。

課題では、設定した評価者の目線で重みを決定し、重みの合計を10にするよう指示されている。

## 4. 判定値と観察項目

観察項目には次の値だけを使用し、`Partial`は使用しない。

- `Yes`：該当する作業に取り組んだ形跡が確認できる
- `No`：該当する作業の形跡が確認できない
- `判定不能`：不鮮明、見切れ、ページ不足などで判断できない

観察項目：

- P1_関連マトリクスによる評価
- P2_評価者と重み付けの設定
- P3_評価表を選択した理由の説明

## 5. P1_関連マトリクスによる評価

提案した代替案を複数の評価項目で比較する表への取組を確認する。

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「関連マトリクス」「評価表」「代替案評価」などの見出しと表がある
- 複数の代替案と複数の評価項目を対応させた表がある
- 各代替案について、評価値、記号、数値などが入力されている
- 少なくとも1つの代替案を複数の評価項目で評価している
- 一般的な見本と形式が異なっていても、代替案を評価項目で比較しようとした形跡がある

次の問題があっても、取組が確認できれば`Yes`とする。

- 評価項目が6項目未満
- 代替案が1つだけ
- 評価値の尺度が不明確
- 一部に空欄がある
- 合計点がない
- 順位がない
- 計算式に誤りがある
- 行と列が見本と逆になっている
- 評価項目の選び方に改善の余地がある

### Noまたは判定不能とする条件

- 「関連マトリクス」という見出しだけで表がない：`No`
- 代替案を列挙しただけで評価値がない：`No`
- 評価項目だけを列挙し、代替案との対応がない：`No`
- 課題と無関係な表しかない：`No`
- 表が不鮮明で内容を確認できない：`判定不能`

## 6. P2_評価者と重み付けの設定

次の作業をまとめて確認する。

- 評価者または評価する立場の設定
- 評価者の目線に基づく重み付け
- 評価項目ごとの重み
- 重みの合計を10にする試み

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「評価者」「評価する立場」「視点」などが明記されている
- 来場者、出店者、運営者など、誰の目線で評価したか分かる
- 各評価項目に重みが設定されている
- 重みの合計値が示されている
- 合計が10でなくても、評価者を設定し、重み付けを行おうとした形跡がある
- 評価者と重みが別の場所に書かれていても、両方を確認できる

次の問題があっても、取組が確認できれば`Yes`とする。

- 重みの合計が10になっていない
- 一部の項目に重みがない
- 評価者の説明が短い
- 重み付けの理由がない
- 重みがすべて同じ
- 評価者の目線と重みの対応が弱い
- 重みと評価値を取り違えている箇所がある

### Noまたは判定不能とする条件

- 評価者も重みも確認できない：`No`
- 評価値だけがあり、評価項目の重要度を示す数値がない：`No`
- 「重要」と書かれているだけで、重み付けをしていない：`No`
- 誰の視点で評価したか全く分からない：`No`
- 評価者または数値を読み取れない：`判定不能`

## 7. P3_評価表を選択した理由の説明

### 課題文の解釈

課題文の「（1）の評価表をもとに、なぜその手法が選択されたのかの理由を述べなさい」は、作成した評価表や評価結果を踏まえて、選んだ代替案または評価方法の理由を説明する作業として扱う。

提出物の表現に応じて、次のいずれも認める。

- なぜその代替案を選んだか
- なぜその評価結果になったか
- なぜその評価項目や重みを設定したか
- なぜ関連マトリクス法による評価を採用したか

### Yesとする条件

次のいずれかを確認できれば`Yes`とする。

- 「理由」「選定理由」「考察」「評価結果」などの見出しと文章がある
- 評価表の結果を引用し、なぜその案を選んだか説明している
- 評価項目や重みを設定した理由を説明している
- 評価者の視点と、評価結果の関係を説明している
- 見出しがなくても、評価表を踏まえた理由を文章から読み取れる

次の問題があっても、取組が確認できれば`Yes`とする。

- 理由が短い
- 評価表の数値を具体的に引用していない
- 目標や目的とのつながりが弱い
- 評価者の視点が十分に説明されていない
- 評価項目だけを根拠にし、目標や目的に触れていない
- 選択理由の妥当性に疑問がある

### Noまたは判定不能とする条件

- 理由の文章がない：`No`
- 「点数が高かったから」だけで、何が評価されたか全く説明していない：`No`
- 評価表を再掲しただけで、理由を説明していない：`No`
- 「良いと思った」「楽しそう」などの感想だけである：`No`
- 課題と無関係な理由しかない：`No`
- 文章が不鮮明で内容を確認できない：`判定不能`

## 8. 誤判定防止

- 同じ評価表だけを、根拠なくP1～P3すべてに数えない。
- P1は、代替案を評価項目で比較する表への取組を確認する。
- P2は、評価者の設定と重み付けへの取組を確認する。
- P3は、評価表や評価結果を踏まえた理由の説明を確認する。
- 内容や計算に誤りがあっても、作業への取組があれば`Yes`とする。
- 見出しだけで内容がなければ`No`とする。
- 不鮮明、見切れ、ページ不足は`判定不能`とする。
- 学生の意図を根拠なく推測しない。
- 評価の正確性や選ばれた案の良し悪しを点数へ反映しない。

## 9. 作業点

P1～P3の`Yes`の数から、作業点を機械的に決定する。

- `Yes`が3個：2点
- `Yes`が1個または2個：1点
- `Yes`が0個で、すべて`No`：0点
- 提出物なし：0点

内容や計算の良し悪しを理由に作業点を下げない。

## 10. 判定不能の処理

`判定不能`を`No`として扱わない。判定不能がある場合は次のように処理する。

1. `Yes`と確認できた項目数だけで暫定作業点を計算する
2. `暫定点=true`とする
3. `人間確認必要=true`とする
4. 判定できなかった観察項目名と理由を`人間確認理由`に記載する

例：P1=`Yes`、P2=`判定不能`、P3=`No`の場合、`Yes`は1個なので暫定作業点は1点とする。人間確認後に2点へ変更される可能性がある。

## 11. PDF形式

従来のプレ課題の規則に従う。

- PDF：`PDF形式減点=0`
- PDF以外：`PDF形式減点=-1`
- 提出なし：`点数=0`
- 遅延：減点なし

提出形式はVLMに推測させない。将来的に`grader.py`が、採点対象となった元ファイルの拡張子から判定する。今回は`grader.py`を変更しない。

## 12. フィードバック

プレ課題では、不足している作業を簡潔に伝える。内容の正確性や計算結果は点数に反映しない。最終課題へ向けた参考として、明らかな不足を一つだけフィードバックへ記載してもよい。

使用できる例：

- 「関連マトリクス、評価者と重み、選択理由の3つへの取組が確認できました。」
- 「代替案と評価項目の対応が分かる関連マトリクスを作成してください。」
- 「教科書に示された評価項目から6項目以上を使用してください。」
- 「どの立場から評価するか、評価者を明記してください。」
- 「評価者の目線から各評価項目へ重みを設定し、合計を10にしてください。」
- 「評価表の結果だけでなく、目標や目的との関係も含めて選択理由を説明してください。」
- 「PDF形式で提出してください。」

## 13. 出力JSON

説明文やMarkdownのコードブロックを付けず、次の構造のJSONだけを返す。

```json
{
  "点数": 2,
  "暫定点": false,
  "観察項目": {
    "P1_関連マトリクスによる評価": "Yes",
    "P2_評価者と重み付けの設定": "Yes",
    "P3_評価表を選択した理由の説明": "Yes"
  },
  "観点別評価": {
    "取組状況": "関連マトリクス、評価者と重み、選択理由への取組が確認できる",
    "提出形式": "PDF形式で提出されている"
  },
  "配点内訳": {
    "作業点": 2,
    "PDF形式減点": 0
  },
  "減点理由": [],
  "評価理由": "指定された3種類の作業すべてへの取組が確認されたため、作業点は2点",
  "フィードバック": "",
  "人間確認必要": false,
  "人間確認理由": []
}
```

## 14. JSONの制約

- `点数`は0、1、2のいずれかとする。
- `暫定点`と`人間確認必要`はJSONのbooleanとし、文字列にしない。
- P1～P3は`Yes`、`No`、`判定不能`のいずれかとする。
- `Partial`は使用しない。
- `作業点`は0、1、2のいずれかとする。
- `PDF形式減点`は0または-1とする。
- `点数`は`max(0, 作業点 + PDF形式減点)`と一致させる。
- 提出なしは0点とする。
- 判定不能が1つでもあれば`暫定点=true`とする。
- 判定不能が1つでもあれば`人間確認必要=true`とする。
- `人間確認必要=true`の場合は`人間確認理由`を空にしない。
- 遅延による減点項目を作らない。
- 教え合いを採点項目に含めない。
- 内容や計算の良し悪しを点数へ反映しない。
- 同じ不足を重複して減点しない。
